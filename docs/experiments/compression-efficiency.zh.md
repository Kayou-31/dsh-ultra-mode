# 压缩效率：分离触发门槛与压后软目标

高效配置把“什么时候开始压缩”和“本次尽量压到多少”分开。旧配置只使用 `contextTargetTokens`：既作为触发门槛，也作为压后软目标。新增的 `contextTriggerTokens` 可让长任务在约 420K 包络触发后，继续回收已持久化的短工具结果，向 30K 软目标收缩。没有配置新字段时保持原行为，压缩默认仍关闭，不新增模型调用。

本页说明机制与实验口径。旧压缩配置的 `recovery-1` 基线在恢复后完成 **30 个合格独立周期**；高效 A 为 **0 个合格周期**，高效 B 为 **27 个合格周期、failed**，第 11 周期含预留已超过 130K。完整旧阶段归档 C-b 的显式恢复最终为 **failed，14／30 合格周期**；已测 14 周期首个压后输入含预留不超过 62,902，测试范围内任务与进度保持一致。用户接受按此部分结果发布，不等于完整 30 轮、模拟一天或永久无损已达标。最终包也不能继承旧候选或离线结果；详见[实验说明](../OCG-EXPERIMENTS.md)及发布收据。

[14 轮首实际压后图](results/ocg-archive-recovery-context.svg)和[逐轮 CSV](results/ocg-archive-recovery-context.csv)保留首实际／首分桶一致请求的区别；[三组描述性图](results/ocg-efficiency-compare.svg)及[数据](results/ocg-efficiency-compare.json)按 30／27／14 分别展示，没有等工作量费用节省或完整归档 30 轮声明。

## 配置入口与默认值

完整 Ultra 的配置 ID 为 `ultra-mode`，独立 Memory 为 `ultra-memory`。组合安装时，在活动证据权威的配置中设置，优先级为 Memory > Ultra > Decision，不把多份配置合并。压缩字段保存在宿主 profile patch，加载时执行插件 schema 和运行层校验，不另存密钥。官方 0.2.1-rc.2 Web 的插件详情是只读清单，没有通用插件字段表单；不要将文件配置验证写成浏览器开关验证。普通子代理的模型候选另有会话输入框旁的模型池界面。

| 字段 | 默认值／范围 | 作用 |
| --- | --- | --- |
| `contextCompression` | `false` | 显式启用宿主原生历史替换；关闭时不压缩 |
| `contextTargetTokens` | `30000`；4,096～1,000,000 | 压后软目标，包含输出和后续工具预留；也用于路线上下文装配 |
| `contextTriggerTokens` | 省略；4,096～1,000,000 | 省略时沿用 target；配置后须大于或等于 target，运行层也校验 |
| `contextRetainRecentMessages` | `8`；2～128 | 保护近期可见消息窗口 |
| `contextMinResultChars` | `4096`；64～1,000,000 | 可压缩工具结果的最小字符数；有来源不等于一定有压缩收益 |
| `contextMaxPrunes` | `16`；1～256 | 单次压缩事务最多替换多少条结果；不是独立压缩周期数 |
| `contextPreviewChars` | `320`；0～4,096 | 原定位格式中的首尾预览长度 |
| `contextCompactLocators` | `false` | 精简定位格式，仅保留来源、原始 seq、结果状态和读回入口；不在每条结果重复项目状态、全体共享 ID 或预览 |
| `contextRetrievalReceipts` | `false` | 允许为本地 `ultra_memory_search/get` 返回建立宿主恢复收据，从而压缩其正文；不压 `ultra_knowledge_*` 返回 |
| `contextArchiveCompletedTurns` | `false` | 实验性已完成阶段归档；保留精确用户要求和公开进展，用 `arc_` 恢复入口按需读回旧工具阶段；真实 130K／30 轮验收尚待完成 |
| `contextOutputReserveTokens` | `4096`；256～100,000 | 输出预留 |
| `contextToolReserveTokens` | `2048`；256～100,000 | 后续工具交互预留 |

`contextCompactLocators:true` 时不使用逐条首尾预览，`contextPreviewChars` 仍保留供原格式使用。**短工具结果不需要普遍压缩。默认单结果路径保留调用记录；只有显式启用完整旧阶段归档，才将配对平衡的旧调用与结果整段移出可见上下文，原文仍留在宿主日志。** 默认门槛仍为 4,096 字符；64 字符只是本次极限实验参数，不是推荐日常配置。只有恢复定位确实比原结果更小、来源可核验时才替换；即使 token 净收益为正，也要计算本地检查与持久化开销，不能以替换条数评价收益。

## 独立实验配置

下面只用于本轮显式授权的独立验收 profile，不能作为日常配置的新默认值。将字段合并到选定插件的同名 patch，保留其他 bundle 和权限配置：

```yaml
contextCompression: true
contextTriggerTokens: 420000
contextTargetTokens: 30000
contextRetainRecentMessages: 2
contextMinResultChars: 64
contextMaxPrunes: 256
contextPreviewChars: 0
contextCompactLocators: true
contextRetrievalReceipts: true
contextOutputReserveTokens: 8192
contextToolReserveTokens: 2048
```

验收启动器用 `--workflow-compression-profile baseline|efficient|archive-130k` 显式选择，省略时仍为 `baseline`；该选项只适用于 workflow。它不会更改日常 profile、自动增加路线或默认发起付费调用。`efficient` 使用上方 64／256 极限参数；`archive-130k` 使用默认的 4,096 字符／最多 16 条单结果替换，加上显式 `contextArchiveCompletedTurns:true`，不是为了少量短结果而普遍压缩。两种参数均为实验配置，不表示已经成为推荐日常值。

本轮单 Agent 总包络上限为 500,000 token。触发判断采用本地 decoded-message 估算与官方 usage 锚定的 native pressure 两者较大值，再加 8,192 输出和 2,048 后续工具预留；这些数始终标作估算。420,000 是含预留的触发包络，不等于精确的 420,000 实际输入；在此配置下，纯输入估算边界约为 409,760。

实际请求另按 provider 回执检查：完整实际输入（包含缓存命中输入）加 8,192 + 2,048 应不超过 500,000。上面的插件配置不能独自建立精确 tokenizer 硬限制；本轮运行器另做请求准入及实际用量核验。压后 30K 同样包含预留，因此不是承诺留出 30K 原文输入，也不是整个任务的累计 token 预算。

## 回收什么，怎样读回

默认单结果路径只替换保护窗口外、调用与返回完整配对的纯文本工具结果。用户原话、assistant 消息及工具调用记录、近期消息、图片及其他 rich 附件在该路径保持原状。额外启用完整旧阶段归档时，才按完整平衡阶段替换旧调用与结果，并逐字保留用户要求与公开进展，见下方归档说明。两条路径均不拆散配对，不提炼或展示原始私有 reasoning；完整原文仍在宿主追加日志，表面替换不删除原始事件。

普通工具结果继续使用已有证据来源。短结果在满足持久化、收益和权限检查后，也可替换成更小的恢复定位。最新项目状态与共同约束通过恢复入口提供，精简格式只取消每条工具结果里重复的副本，不删除这些权威内容。

高效 A 组暴露了另一类一致性问题：模型将已执行操作的 receipt 错列为被替代的决定。修正是在精简恢复入口加入通用类型约束：决策历史只记录有来源的决策／策略版本及替代关系；commit、test、receipt 和已执行操作属于操作账本，不能因较早发生就标为 superseded 决策。提示不含本实验的操作 ID、业务答案或期望版本，也不放宽评分；B 组后续取得 27 个原判据合格周期，但整体仍 failed，不能因此声称已验证所有类型混淆都得到解决。

本地检索返回使用 `contextReceipt:true` 的标准来源记录作为恢复收据。收据只保存项目／会话／事件定位、工具与 call ID、长度和 SHA；不复制返回正文，不生成正文分块或词索引。建立收据前，必须从同一会话的宿主持久日志校验原文及调用身份；不存在、损坏或不匹配时保留原结果。

恢复时沿用 `ultra_memory_get`：使用占位中的 ID，按 `offset`、`maxChars` 分页；已读到的精确引文可用 `quote` 核验原文 SHA 和来源工具。读回继续执行原项目／会话访问边界、最终返回预算与完整性检查。响应标记 `contextReceipt:true`，表示历史检索返回，只能作为资料，不能成为新用户指令或授权。同正文被替换成另一个 call ID 时返回 `identity-mismatch`，不提供正文。

收据不会进入共享近期事实列表、默认 `recordsFor`、原文搜索、语义提炼、项目状态、主题 MD 或全局发布候选。覆盖统计单列 `contextReceipts`，不把它计成新增完整原文索引或语义成果。被检索的原始证据仍通过自己的来源 ID 搜索与核验。全局知识返回继续保留原文，不通过本地恢复收据绕过知识读者或撤销规则。

## 一致性与恢复边界

压缩先完成持久化和来源校验，再通过官方 prune／replace 协议替换可见历史；每条替换保持原消息及工具调用身份。单结果路径在提交前失败不改原表面；替换后失败时使用补偿事务恢复原表面，并单独记录恢复 checkpoint 是否持久。完整阶段归档的跨角色替换不具有同一补偿保证，提交后持久化不确定时停止后续调用，不能宣称精确回滚。取消、证据权威关闭和其他 compactor 接管都不会授权继续删除历史。原始追加日志及旧失败记录保留，不把失败改写成通过。

30K 是尽力达到的软目标。受保护的用户要求、assistant 历史、调用配对、近期或 rich 内容、替换次数限制以及不可恢复来源，都可能使压后上下文高于目标；这时应显示剩余限制，不为压缩率丢弃必要材料。一次事务替换 24 条结果仍只算一次周期，不能当作 24 轮验收。

高效 B 组已结束，保留 failed：368 条 controller 观测、367 个 gate 准入与结算、27 个原判据合格周期；1 条观测未映射到 gate，8 个 gate usage 未知。末次错误仅有 `UNKNOWN` 分类。第 11 周期压后含 10,240 预留为 138,797，第 27 周期为 288,535，均未达到新增的 130K 目标。基线额外冷读回的 9 次调用／6 份此前未引述原文行已独立通过，结果、业务文件和原生主前缀不变；这是 f0c 基线的额外验证，不是新归档机制或最终包的通过证据。

基线组与高效组复用同 seed 和冻结工程 fixture，但报告行数按上下文动态分配。高效组的报告分配目标为 **445K**，基线为 **430K**，用于给回收短结果后的上下文留出生成报告的空间；这是运行器估算分配目标，不是 provider 实际输入。两组不是等工作量的总账单 A/B，不能将总 token 的差值直接归因于压缩。应分别报告合格周期、实际输入缩减、压后增长、质量及用量。

## 升级与降级

### 130K 目标的新增归档路径

归档 C-a 首次实机尝试记录 10 次真实调用、0 个合格周期。实际大输入为 445,590，含预留 455,830，没有超出 500K；失败发生在提交后的原生 JSONL 校验：成功的 `compaction/end` 必须有一条 `compaction/summary`。原失败、用量和原始日志均保留，不归因于模型漂移，也不拿单纯 Session/fold 回放通过代替真实持久化。

修复采用宿主支持的本地确定性 template 记录，backend 标识为 `dsh-ultra-local / completed-turn-archive-v1`；`summary` 存放同一精确公开恢复胶囊，并不是一次模型摘要。生命周期为 start → summary → user checkpoint replace → end，不同时追加同跨度的 prune 以免重复影子计价；不填写 `llmStreamCall`、usage、rawOutput 或虚构模型消耗。新增真实 JSONL 专项连续归档 30 次、逐次 flush/read、关闭整个宿主并用新 backend 冷重开，核对原文 SHA、分页恢复和 TokenMeter。后续 C-b 使用新包、新 profile 和单独成绩，不覆盖 C-a。

C-b 原组有 44 个真实正 usage 请求／2 个合格周期，保持 failed。第 3 阶段实际测试、独立原文 get-before-commit 和磁盘 commit 均完成，但 final 的 JSON 代码围栏之后又附说明，严格 parser 返回 `WORKFLOW_INVALID_JSON`。离线截取内部 JSON 不能把原答案改判为通过。
