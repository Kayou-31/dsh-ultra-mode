# 0.4.0-rc.2 候选版验证

记录日期：2026-10-11。目标宿主为 **DSH Desktop / Host 0.2.0-rc.2**。本页记录 rc.1 真实失败及 rc.2 修复后的实际复验：**普通 Agent 单开协作的基础派发、消息排队及同 ID 续作已走通；最终包重装后的新会话复核通过**。验证完成后，于 2026-10-11 发布 [v0.4.0-rc.2 预发布版](https://github.com/Kayou-31/dsh-ultra-mode/releases/tag/v0.4.0-rc.2)，标签对应已合并主分支的提交 `dfa9cd2`，TGZ 与本机实测包一致；正式版仍为 v0.3.2。预发布不表示未测场景已通过验收。

## rc.1 的真实失败

本机真实测试在 Ultra 关闭、协作开启的普通 Agent 场景中，发现首个模型请求没有六个 `ultra_*` 协作工具。模型随后依靠宿主原生派发能力完成任务，计算得到 210／56；运算结果正确只证明该次原生退回路径完成，不能证明新增协作增强生效。

因此 rc.1 在这个场景的增强验收为**失败**。先前 [rc.1 验证记录](verification-0.4.0-rc.1.md) 中的构建、离线回归及界面 fixture 结果保留，它们没有检查到此次真实首请求工具可见性问题，不能覆盖或改写本次失败。

## 接入时机修复

根因是协作工具注册晚于宿主首请求材料的组装。原先在 `agent/pre-step` 调度路径接入时，宿主已经取得工具列表和 system prompt；之后注册工具不能让这一请求自动看到新增 schema。

rc.2 当前源码将协作接入前移：

1. 在真实主 Agent 的 `turn/start` 冻结本次协作选择并预挂载工具，使正常路径早于首请求组装。
2. 连续 turn 与上一组原生排空重叠时，在 `system-prompt/assemble` 等待前次清理，再补挂本次工具。
3. 必要时通过宿主公开组装接口重建完整请求材料，保留 tool order、PTC 呈现及完整 prompt，不手动拼接工具 schema 数组。
4. 挂载失败仍明确记录并保留原生能力；关闭协作、当前组收尾和后续任务选择继续分别处理。

实现入口为 [`src/index.ts`](../src/index.ts) 的协作预挂载和请求组装 hook。修复后真实基础任务的首个请求 header 已记录完整六个协作工具；此证据核对宿主保存的请求材料，不等同于 provider 原始网络正文抓包。

## 普通 Agent 的真实基础任务

测试保持 Ultra 关闭、协作开启。实际记录包括：

- 首个请求 header 中有 `ultra_spawn_agent`、`ultra_send_message`、`ultra_followup_task`、`ultra_wait_agent`、`ultra_interrupt_agent`、`ultra_list_agents` 六个工具，而非只出现说明文字。
- 2 个子代理由增强 wrapper 实际派发，委派深度为 1，思考档位继承 High，provider/model 与主 Agent 路由一致，没有被协作层强制改成 Max。
- 两个子代理分别得到 210／56，主 Agent 自己得到 97，合计 **363**。父 Agent 保留普通执行与汇总职责。
- 完成 2 次成功的增强等待，第二次携带前次 cursor。

**保留的错误：**模型第一次调用 `ultra_wait_agent` 时传入 `timeout_ms: 120000`，超出本工具允许的 0–60000 毫秒范围，被参数边界拒绝；随后修正并恢复完成。最终结果成功不等于全程零错误，也不能把这次拒绝从记录中删掉。

## 非唤醒信息与显式续作的真实任务

第二个主 turn 中，模型实际按以下顺序使用增强工具：

1. 派发 1 个子代理，得到 9，并等待其进入 `completed`。
2. 对同一子代理排队发送 37。
3. 查询状态仍为 `completed`，表明这次信息排队没有将空闲目标改成执行中的状态。
4. 显式调用 `ultra_followup_task`，复用同一子代理 ID。
5. 后续增强等待取得 **46**。

界面显示本轮约 14 秒，只作为该次宿主界面观测，不作为独立延迟基准或性能优势。运行时账本独立核对通过：6 次主工具调用全部成功，14 项断言通过；子代理的两次请求保持相同模型及 High，原生完成通知与两个 activation 对应。

## 最终文案与包的复验

针对真实基础任务中出现的 120000 毫秒参数误用，源码已补充等待工具的参数描述：`timeout_ms` 范围 0–60000、默认 30000；`targets` 为 1–8 个子代理；`after_cursor` 使用上次返回的 cursor。它与宿主原生等待工具的参数习惯分别说明。

最终候选已重新打包、安装并在新会话复核，安装后的四个核心 JS 文件与构建产物哈希一致。首请求包含全部六个工具；两个 wrapper 子代理继承 High、深度 1，返回 210／56；主结果 363。两次等待分别使用 60000／30000 毫秒，第二次携带 cursor，主与子工具错误均为 0，10 项断言全部通过。两个原生 finished 通知均早于主 turn 结束，支持该次 activation 已收尾；不冒充实时 registry 检查。界面显示约 10 秒，只是本次观测。

此前 120000 毫秒越界及恢复记录继续保留，不能据最终一次零错误声称所有试验均零错误。最终包哈希在包外交付记录核对；打包内文档是运行前快照，本仓库记录补充了后续实际结果。本页不公开本机路径、真实会话 ID、密钥或思维链。

## CI 时序失败与测试修复

首次提交的 Linux CI 通过，Windows CI 在辅助首测试中出现 `2 !== 1`。测试将首轮已解析的响应 Promise 重用于后续合法检查，慢调度下会回放同一条建议。修复为独立挂起的后续响应，并用真实反馈事件同步等待，未增加 sleep 或改变运行时代码。目标测试连续 10 次通过，完整辅助测试 17 项通过，全量本机仍为 177 项中 176 通过、1 项环境限制跳过。该失败记录保留，最终跨平台 CI 以 PR 检查为准。

## 保留的限制

真实结果覆盖首请求工具可见性、增强派发、继承 High、等待/cursor，以及信息排队后同 ID 续作的短任务。未在此记录中验收真实中断、取消/卸载收尾、反复长任务或 Ultra 组合模式；六个 schema 出现不代表六个工具都完成了真实行为验收。算术任务通过也不证明业务质量、Token 成本或延迟优于普通 Agent。现有 [业务案例](../benchmarks/README.md) 的离线自检不能代替真实模型多次对照。
