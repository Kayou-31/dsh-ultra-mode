# OCG 实机实验与验证边界

本文记录开发过程中的实验，区分真实模型、原生离线脚本、单元测试与界面操作。**旧压缩配置的恢复基线完成严格 30 周期；归档 C-b 的显式恢复最终以 failed 结束，完成 14／30 个合格周期，未达到一天工程时间线或完整 30 轮目标。** 用户明确接受按此部分结果收尾发布（`userAcceptedPartial:true`），发布不改变实验判定。高效 B、C-a、原 C-b 和恢复失败分别保留；没有继续付费重试或启动归档额外冷读回。新包的构建及原生复核以同批发布收据为准，不能继承旧候选的全部成绩。

本轮主要验收采用[500K 总上限、420K 触发、30 次独立压缩规范](experiments/workflow-500k-30-spec.zh.md)，不再用旧 14 / 26 轮填充压力组代替正常工作流。项目模拟时间与实际工作耗时分别记录，基线结果与新机制待验证项分别报告。

## 环境与计数

主验收宿主固定为官方 **DSH 0.2.1-rc.2**，使用独立 profile、DSH_HOME、OS home、合成项目和临时目录。第三方桌面应用不作为本轮宿主；没有将测试插件安装到日常环境。在线阶段仅使用用户授权的 OCG 通道和所选凭据，网络守卫限定已授权服务来源。用户已取消双并发限制，运行器仍有显式、有限的并发、请求与时间预算。

多数真实调用使用 **DeepSeek V4.1 Flash**；同时有一组涉及五个模型的短工具 smoke，不能称为五个模型都完成长期验收。同一服务下两个不同模型的选模实验，不能外推为跨 provider 的数据授权或所有模型兼容性。

文中的 calls 是运行器观察到的原生 `llm/stream` 调用，不等于独立核验的 HTTP 发包数或账单次数。provider 报告的 usage、缺失 usage、宿主 token 估算和实际费用分别记录；订阅额度不能换算为已实测成本。任务轮数、请求数、prune 事件数和独立合格压缩周期也分别统计。

旧工作流之前的白名单汇总 `ocg-dev4-preworkflow-public.json` 已生成，SHA256 为 `d77a1b11c58767aeac5e4774611fd0ecb65f6e4e6c9bc81dd5494d9131e43484`。它只覆盖明确登记的 30 份收据：**329 个唯一请求，320 completed／9 failed**；320 个请求有 provider usage，合计已报告 `totalTokens` **24,666,958**。各字段独立求和：`inputTokens` 9,021,996、`outputTokens` 387,801、`cacheReadTokens` 15,255,588、`cacheWriteTokens` 1,573，`reasoningTokens` 未报告。不同模型对缓存字段的口径可能不同，不重建 total，不再把缓存或 reasoning 加到 total 上。另 9 个请求用量未知，费用为 null。

## 500K／420K 正常工程工作流

正式 **30-a 因预算误拒停止，30-b 因收尾 TRANSPORT 失败停止；原失败均保留**。30-a 记录 17 次 `llm/stream` 观测，其中 16 次为有 provider usage 的实际调用，第 17 次在准入 guard 处被拒，未发出该次大请求；独立压缩周期为 0。30-b 使用同一 seed 和新冻结候选，在新的独立 profile 完整重启一次，不续写 30-a 或继承其通过计数。固定官方 DSH 0.2.1-rc.2、OCG `deepseek-v4.1-flash`、low、单并发，使用新的独立 profile 和合成订单对账工程。单 Agent 总窗口为 500,000 token，压缩软触发包络为 420,000，近期窗口 retain=2；900 请求和 3 小时是有限退出上界，不是预计消耗或已完成时长。时间上界参考校准 C 约 214 秒控制器工作耗时乘 30，并给大报告 prefill 留出余量，不承诺一定在预算内完成。

模型按阶段读取原始规范、计算期望值、修改验收测试模块并真正执行 Node 测试，再独立检索原始报告、核对 SHA 和完整 JSONL 行后提交。业务计算核心及独立 oracle 由 fixture 预置，因此这是持续验收工程，不是模型从零实现全部业务。后续要求分阶段进入，未来规则／答案不作为初始提示公开。工程时间线跨度为 **24 小时 10 分钟**；这与实际墙钟耗时不同，未做墙钟 24 小时耐久验证。

420K 包含 8,192 输出和 2,048 后续工具预留。产品复用官方 token meter 的 usage 锚与 surface 变化估算作为 native-meter floor，并与本地 decoded-message 估算取较大值。后者计入解码后的正文、工具参数、reasoning、消息 framing、工具定义及 rich／unknown 结构回退，避免把工具 JSONL 的 JSON 传输转义和宿主消息 metadata 当成额外模型内容。两种方法均不是 exact tokenizer，数值仍标为 estimated，可能早于实际 420K 输入触发，不保证压缩无损。500K 模型目录值也不是 provider 精确 tokenizer 硬保护。运行器以实际请求准入和 provider 回执分别核验含缓存输入及预留；缺回执、超窗或未到触发口径的事务不计合格周期。详见[完整验收规范](experiments/workflow-500k-30-spec.zh.md)。

30-a 的 899 行真实 Node 报告为 1,279,865 bytes；旧估算对整条工具消息再次 JSON 编码，因转义膨胀将含预留预算估为 518,237 并拒绝。离线重建当时的完整原生可见消息和 request/header 后，旧预算可精确复现；使用修正后的 decoded-message 计量，新预算为 **463,595，estimated**。这是同一未发送输入的离线预算对照，不是 provider 实测输入或大请求已成功发送的证明。30-a 保持失败。30-b 原组有 18 次 gate 准入，17 completed／1 failed；虽然已观察到真实大输入、原生正文替换、原文读回和提交，收尾模型连接仍因 TRANSPORT 失败，因此原组保持 **0 个合格独立周期**，不能改写为首次通过。

对 30-b 的授权恢复单独登记为 recovery-1：沿用同一 seed、隔离工程、会话与冻结产品候选，不重跑已提交阶段。已完成提交但 final 连接失败时，冷恢复仅只读补齐该阶段 final 核验，不重复旧工具变更或提交；随后继续新阶段。控制器、原生终态重判与独立审计现已一致确认 **30 个合格独立压缩周期通过**，固定质量检查、原文 SHA、整行引文、get-before-commit 及实际用量边界均核验。这是恢复后闭环，不是原 30-b 首次通过。

该基线累计 **364 个 gate 准入：360 completed／4 failed**。原 18 个请求为 17 成功／1 失败，恢复新增 346 个请求为 343 成功／3 失败；旧 18 条观测只作为继承前缀，不重复记消耗。4 个失败调用的实际消耗未知，不将错误流中的 0 usage 当作已实测零费用。控制器累计工作耗时 **4,407,988 ms，约 73.47 分钟**，另有启动和恢复空档；工程时间线为 **24 小时 10 分钟**，不是墙钟运行满一天。

第 1／10／20／30 阶段实际压前→压后输入为 **431,467→14,994／430,346→122,400／429,797→244,238／429,985→363,182**，都包含缓存命中输入，未混入输出预留或累计 token。末轮达到任务一致性与 500K 包络验收，但长期残留明显增长，不能因此承诺每轮压回 30K。该结果仅归 f0c 冻结基线及明确记录的恢复；额外冷恢复检查点探针已暴露新问题，其修复与最终包复验仍待关闭。

恢复仅在显式验收 profile 配置官方有界重试：只允许 TRANSPORT，最多 2 次，其他策略及产品默认重试仍为 0。账本依唯一 gate ID 与最后 provider usage 去重，已知小计与未知消耗分开。基线 30 周期的终态已核验；高效 B 组、额外冷恢复及最终构建不能继承这项通过结论。

基线完成后的额外冷读回已获独立审查通过：**9 个真实请求、6 份此前未引述的完整 generated 行**，固定阶段 1／6／11／16／22／27，要求新 search/get 回执、来源 SHA 与整行 checksum；只开放检索，无业务变更，主结果、业务文件和原生主前缀冻结后保持不变。这是另行登记的恢复验证，不增加主 30 周期数；原报告曾进入主模型，不能称这些行从未被模型看过，也不能归给后续新包。

### 高效短结果 A／B 均保留失败

高效 A 组 `ocg-wf-efficient-30-a` 有 **23 个成功调用、0 个合格周期**：大输入、原文 SHA、完整引文及提交均完成，但最终答案把已执行操作 receipt 列为 superseded 决策，固定评分拒绝该类型错误。失败和消耗保留，不能用单次大幅压缩样本替代质量通过。新 B 组使用通用的决策历史／操作账本类型约束，不注入 fixture 的 ID 或答案，不放宽判据。

启动器显式提供 `--workflow-compression-profile baseline|efficient`，缺省仍为 baseline。efficient 将 420K 触发和 30K 压后软目标分离，并试验精简定位和本地检索恢复收据。**64 字符短结果门槛仅为本次极限实验，不是普遍推荐；默认仍为 4,096，压缩默认关闭。调用记录及配对本轮保持原状。** 短结果的 token 收益不自动覆盖持久化和恢复开销。

B 组已停止并保留 **failed：368 条 controller 观测、367 个 gate 准入及结算、27 个合格周期**，1 条观测未映射到 gate，不推算为零费用；8 个 gate 的真实 usage 未知。末次错误仅保留 `UNKNOWN` 分类，不编造根因。阶段 11 压后实际输入加 10,240 预留为 **138,797**，已不满足后来追加的逐轮 130K 标准。早期旁路审计中阶段 1～6 压后输入由 11,103 增至 71,629；阶段 6 全部 native pre-step 压缩链耗时合计 12.867 秒，不能只报告大结果那一次替换的耗时。保护的用户、assistant、调用历史、近期消息及宿主必需内容会形成残留，各部分贡献尚未单独计量；早期低输入不构成长期目标通过证明。

两组同业务 seed／阶段规则，但动态报告量不同：基线分配目标 430K、高效组 445K，基线还包含显式恢复，因此不是等工作量总账单 A/B。完整配置、样本表、类型修正和保留历史下限见[压缩效率说明](experiments/compression-efficiency.zh.md)。两次失败的质量、已发生用量和本地开销独立保留，不移入新归档组的通过计数。

### 完整旧阶段归档：保留 C-a／C-b 失败，C-b 从第 3 阶段显式恢复

归档只在实验显式启用 `contextArchiveCompletedTurns`，默认仍关闭。它归档完整结束且工具配对平衡的旧阶段，以平坦清单保存 canonical 来源定位；用户／控制文字和公开 assistant 文字逐字进入恢复胶囊，工具参数与结果正文留在宿主原生日志按需读回。系统／开发者指令、当前与近期阶段、富媒体和全局知识等受保护区域不因此移除，私有 reasoning 不进入公开恢复文本。

**C-a 有 10 个真实正 usage 请求、0 个合格周期，保持 failed。** 原生 start→prune→user→end 已提交后，官方 JSONL 校验拒绝成功 end，原因是缺少必须的 summary 事件；记录为提交后持久化不确定，停止后续模型／业务调用。这是实际宿主协议失败，不作为模型语义偏移或原文丢失的证明。原目录、包、原生前缀及独立失败审查保持原样，不把旧 prune 事务改判为成功归档。

修正采用官方确定性模板协议 **start→summary→user→end**，summary 与同一 sealed capsule 一致，固定本地 `dsh-ultra-local / completed-turn-archive-v1`，不发起摘要模型请求，不填 `llmStreamCall`、usage、rawOutput 或 maxTokens，不再追加 prune 双重计价。summarySeqs 与 pruneSeqs 分开统计；原生 shadow price 仍是宿主估算，不是 provider 实测消耗。提交前失败保留旧表面；提交后失败不能虚称精确回滚。

**C-b 使用新独立目录及候选 `bf1235637d999d50421d33107a23ce61958652e1b385461c7caff121247f1092`，原组保持 failed：44 个真实正 usage 请求、2 个合格周期。** 独立核对确认，第 3 阶段原文 get-before-commit、SHA 和磁盘 commit 已完成；模型最后输出为 JSON 代码围栏之后又追加说明，严格 parser 返回 `WORKFLOW_INVALID_JSON`。离线截取内部 JSON 的诊断不计通过，也不据此认定压缩语义漂移。

显式恢复单独登记在 `ocg-wf-archive-30-b/recovery-1`。同一 session、seed、工程与冻结候选继续执行，16 个原失败文件及原生字节前缀先封存；原 44 个请求只继承一次，新调用上限为 856，合计上限仍为 900。原启动器已耗时 268,422 ms，从 10,800,000 ms 总时限中扣除后，剩余上限为 10,531,578 ms。没有从头重跑，也没有把 C-a 或高效 B 的周期合并进来。

第一个恢复阶段仅补公开 final：1 条新用户指令、0 次工具调用、72 个业务文件在该只读阶段前后未变，新的严格 JSON 答案、来源归属与评分通过；旧第 1／2 阶段和原请求字段保留。第 32～44 个旧请求仅补充可从原生结算重验的 `nativeUsageVerified/nativeSettlementSeq` 派生字段，不改原 usage、finish 或计费记录。随后继续后续工程阶段，最终独立关账为 **failed，14／30 个合格周期**。239 个请求由原 44 个与新增 195 个组成，239／239 原生结算和唯一 gate 均核对；0 个未知失败 usage、0 个 500K 违规、0 次重复成功提交，不将继承前缀重复记账。
